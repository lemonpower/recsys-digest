排序不确定性如何决定推理预算

这期的共同问题是如何把计算留给更难的请求。序列推荐可以先估计排序结果的稳定性，工具检索则可以用混合检索缩小候选范围。

Section 1: 📊 Trend Analysis

  • 🔥 Agent 基础设施化：LLM Agent 的工具调用正从"直连"走向"网关化"，阿里云 MCP Gateway 把协议兼容、权限控制、工具推荐、会话路由统一收敛到网关层，用混合检索在 3000+ 工具上做到 ~98% Top-15 召回。对推荐工程师的启示是：工具选择本质是一个大规模召回+排序问题，传统推荐技术栈可直接复用。
  • 💡 效率优化走向"实例级自适应"：RACE 指出统一压缩率造成 Capacity-Complexity Mismatch，用排序不确定性作为实例复杂度代理，动态决定剪枝力度与序列长度。这类"按需分配算力"的思路对线上推理成本敏感的场景（实时序列推荐、粗排）具备直接迁移价值。
  • 🔍 可解释性从"事后归因"转向"表示层改造"：Doctolib 用 SAE 把稠密 embedding 转成稀疏可解释编码，同时用 InfoNCE 保住相关性，实现域内提升 + 域外少衰减。相比事后解释，这种"可解释表示 + 检索增益"双赢路线更值得关注。

Section 3: 📰 Daily Digest

1. Scaling LLM Agent Tool Access: The MCP Gateway

🔗 原文： https://arxiv.org/abs/2607.15593

🏷️ 来源： 🏭 工业界 | Alibaba Cloud, Nanjing University, Fudan University

⭐ 评分： ⭐⭐⭐⭐ (4/5)

🎯 推荐理由： 工业级MCP网关系统，解决LLM Agent工具接入的可扩展性问题，含工具推荐与路由设计。

📝 摘要： 针对 LLM Agent 工具调用在生产环境难以扩展的痛点——旧服务无法直连 MCP、协议快速演进带来兼容成本、挂载工具数受上下文窗口与推理开销限制、有状态后端多副本会话亲和复杂——论文提出云规模 MCP Gateway，打破数据面直连模型，把旧服务集成、MCP 变体兼容、访问控制、工具推荐与会话感知路由统一卸载到网关。转换模块支持 315 个 OpenAPI 服务，会话感知路由解耦网关层与服务层扩展性，混合检索引擎在 3000+ 工具上维持 ~98% Top-15 召回并提升工具选择准确率。创新点在于系统架构层面的网关化设计与工具推荐召回，并分享了生产部署经验；局限是偏基础设施、缺乏线上 A/B 指标，与 CTR 预估等推荐核心问题关联较弱，但"工具选择=大规模召回"的建模视角对 Agent 推荐方向有直接借鉴价值。

2. Explanations that Transfer: Interpreting Medical Retrieval with Sparse AutoEncoders

🔗 原文： https://arxiv.org/abs/2611.18179

🏷️ 来源： 🏭 工业界 | Doctolib

⭐ 评分： ⭐⭐⭐ (3/5)

🎯 推荐理由： 首次将稀疏自编码器用于医疗检索可解释性，兼顾域内提升与域外泛化。

📝 摘要： 医疗检索依赖稠密 embedding，但其内部机制不透明，且针对特定医疗语料微调易损失跨临床语料的迁移性。论文首次将稀疏自编码器引入医疗 IR，把稠密文本 embedding 转为语义可解释的稀疏表示，训练目标结合重建损失与 InfoNCE 对比损失以直接保持 query-document 相关性。在 3 个嵌入模型、6 个医疗数据集（CURE、MIRIAD、NFCorpus、R2MED 等）上验证：稀疏编码域内检索优于原始 embedding，域外性能衰减小于稠密版本，且目标语料与训练语料差异越大优势越明显。激活特征语义可从触发它的 query/document 反推，能解释"为何召回该文档"并跨分布迁移。属方法迁移型增量改进、仅离线评估无线上验证，但"可解释表示同时带来检索增益"的思路对召回可解释性建设有参考价值。

3. RACE: Ranking-Uncertainty Aware Capacity-Adaptive Customization for Efficient Sequential Recommendation

🔗 原文： https://arxiv.org/abs/2611.18244

🏷️ 来源： 🤝 产学合作 | Zhejiang University, Huawei

⭐ 评分： ⭐⭐⭐ (3/5)

🎯 推荐理由： 用排序不确定性驱动实例级自适应压缩，兼顾序列推荐精度与效率。

📝 摘要： 现有高效序列推荐普遍采用统一压缩率，忽视用户意图复杂度差异，造成 Capacity-Complexity Mismatch——简单样本浪费算力、复杂样本算力不足。RACE 提出以模型内在不确定性作为主动资源分配器：从 top-K 预测的分布稳定性导出 list-wise 排序不确定性指标，作为实例复杂度的可测代理，再用自监督训练的轻量预测器从浅层特征提前预判该信号。据此做双维度实例级瘦身：超网络式通道敏感性提取器识别参数冗余，重要性感知渐进序列过滤削减数据冗余。四个公开数据集上在精度、效率、自适应三方面均超 SOTA 基线。属模型压缩方向的增量改进，缺乏工业级部署验证，但"按实例复杂度动态分配算力"的范式对实时序列推荐与粗排降本有直接迁移价值。

🎯 今日主题：生成式检索 RL 微调：奖励给到序列级还是集合级？

生成式检索把召回变成 SID 序列的自回归解码，SFT 只能模仿日志里曝光过的那一条路径，无法表达「整页效用」。于是近期的工业系统几乎都在这条解码链上接 RL：JD App 的 GenRec 用 GRPO-SR [JD.com]，阿里电商搜索的 CQ-SID 用 EG-GRPO 把排序信号引入召回 [Alibaba]，UniSearch 把 RL 训练系统与在线 Trie 解码服务直连、持续做偏好对齐 [Kuaishou]，淘宝闪购的 GMPO 则直接把奖励从序列级推到集合级。分歧在于：奖励该给到多细？token 级、rank 级、序列级、整页集合级都有人做。而 [2611.02404] 给出了一条硬约束——当奖励本身依赖同组其他样本时，group-relative baseline 会改变优化目标。这直接决定了粒度选择的可行边界。

组内 baseline 怎么定：曝光锚点、专家样本还是不扰动样本？

GRPO 的立身之本是省掉 critic，用组内平均奖励当 baseline。问题在于推荐场景的日志反馈极度偏斜，正样本稀少，直接按组均值归一化会让策略朝「已经曝光过的东西」自我强化。

最直接的修补来自 ABPO [SK Telecom]：对每个日志 context，把线上策略实际曝光的那个推荐作为固定 anchor 放进 rollout 组，但只用来校准 baseline，不进入 surrogate 的分子。正反馈的 anchor 拿到高 item-matching 奖励、抬高基线；无响应的 anchor 奖励低、压低基线。这样既压制正曝光样本的盲目强化，也缓冲无响应样本的过度惩罚。曝光偏差用 self-normalized IPS（SNIPS）校正，mini-batch 强制分层以同时包含正响应与无响应样本，避免严重不平衡下归一化失稳。目标函数仍是 GRPO 的形式，只改了「baseline 从哪来」和「标量效用怎么算」两处。

CQ-SID 的 EG-GRPO 走的是另一条路 [Alibaba]：稀疏奖励下直接把 ground-truth 样本注入 policy group，用专家轨迹把组内奖励分布撑开。Factorized Latent Reasoning 则更省——组内第一个样本不做高斯扰动，作为稳定基线降方差，其余样本在 `<|Thought|>` 嵌入上注入噪声制造多样性，奖励是 token 级置信度与序列级 exact-match 的混合 [Meituan]。

这些改法背后有理论依据。[2611.02404] 证明：当奖励依赖组内其余样本（多样性、覆盖度、分布匹配这类奖励天然如此），group-relative baseline 会改写目标——期望更新等于「自身奖励梯度 + α × 自己对同组其他样本奖励的影响」，组大小 K 时 α = −1/(K−1)。换言之，vanilla GRPO 训练每个 response 去击败同组伙伴，是一场零和锦标赛，pairwise 的多样性 bonus 根本看不见。这条结论对「集合级奖励」是致命的：整页/整列表效用本质上依赖同组其他候选，直接套组均值 baseline 就把协作目标变成了内斗。要上集合级奖励，就必须像 ABPO 那样换掉 baseline 的来源，或者像 Rank-GRPO 那样换粒度。

token、rank、序列还是整页：粒度决定了 credit 落在谁头上

Rank-GRPO 对这个问题给了最明确的三分法：token 级「太细」，序列级「太粗」，于是以「列表中的每个 rank」为单元做 credit assignment，并用 rank 内各 item token 概率的几何平均构造 rank-level importance ratio 来稳定更新 [Netflix]。它点名的反例是 RecLLM-R1——直接生成列表却用 sequence-level 奖励做 token-level 更新，与排序任务的结构错配，性能被 vanilla GRPO baseline 限制住 [Netflix]。在 REDDIT-V2 上，这种 rank 级设计比 GRPO-style baseline 收敛更快、Recall 与 NDCG 更高 [Netflix]。

GenRec 选择把粒度推到「页」：Page-wise NTP 监督整个交互 page 而非单个 item，梯度信号更密，同时化解 pointwise 训练的 one-to-many 歧义；RL 阶段是 GRPO-SR，即在 GRPO 上叠一个 NLL 项防止策略漂离 SFT 锚点 [JD.com]。注意这不是集合级奖励，而是集合级监督配序列级奖励——用更密的监督补上奖励粒度的不足，是比改奖励更便宜的一条路。

重排侧的思路是拆成 generator-evaluator：evaluator 拟合 list-level utility 充当用户响应模拟器，generator 负责在指数级排列空间里探索 [Alibaba][Kuaishou Technology]。多 generator 版本进一步用 list reward estimator 在多个生成器产出的候选列表里择优 [Kuaishou Technology]。这里的固有代价是目标不一致——evaluator 优化的是列表级价值，generator 只能间接感受 [Alibaba]。

采样开销是选粒度时绕不开的实际约束。token 级每步要 N 条完整 rollout × 序列长度；rank 级只在 rank 维度重加权，rollout 数不变但方差更小；page 级必须一次解出整页。工业系统的降本手段很具体：GPR 用 beam search 生成 K=40 个候选广告，每个候选按 L 级 SID 分层解码，奖励由复制生产 pCTR/pCVR 排序模型的仿真环境给出，避免实时调用重模型 [Tencent]；GenRec 用非对称线性 Token Merger 把 prompt 里的多 token SID 压缩，输入长度降约 2 倍而解码仍保持全分辨率 [JD.com]。

最后别忘了阶段差异：召回要 coverage、排序要 discrimination，而生成式检索共享同一套 codebook，天然在簇内细粒度区分上吃亏 [JD.com]。所以在召回阶段用序列级奖励换覆盖率、在重排阶段用集合级奖励换整页效用，本身就是合理的非对称选择。

多目标怎么压成一个标量：权重写死在奖励里还是可切换？

工业系统的奖励从来不是单目标。GPR 的做法最直白：候选的奖励等于预测 eCPM 加上若干辅助目标的加权和，pCTR、pCVR 这些 target 各带一个显式权重，权重写死在奖励函数里，由仿真环境统一评估 [Tencent]。好处是可解释、可调，代价是权重本身成了超参，且要知道各目标的量纲。

更根本的质疑来自 [Netflix]：推荐反馈天然是标量（评分、观看时长、评论），这与 DPO 需要的二元偏好对并不兼容；而 learned reward model 跨全 item catalog 泛化差是核心瓶颈，任何在训练时查询 reward model 的方法都继承这个失败，与上层用 PPO 还是 GRPO 无关。它的结论偏保守——介于 offline RL 与 behavior cloning 之间的指数奖励加权 SFT 反而优于 RLHF 路线。这条结论值得每个准备上 RL 的团队先验证一遍。

折中方案是把多目标交给策略结构而非标量奖励。Steerable Multi-Objective Group-Relative Preference Optimization 用联合训练的多个 LoRA adapter 承载不同目标偏好，实现可 steering 的组相对优化 [researchgate.net]；电商 shopping agent 侧则直接用生成式奖励模型 E-GenRM 输出奖励 [Alibaba]。对齐下游排序信号这条线也有现成做法：CQ-SID 的四阶段训练最后一步就是 ranking-aligned refinement，让生成式召回与排序打分同向 [Alibaba]；Factorized Latent Reasoning
